# Three-minute scripted productivity controls

`scripted-native-productivity-v2` is an explicit successor to the historical
120-second `scripted-native-productivity-v1`. It is a scripted environment
experiment, with no model, zero API requests, `score:null` and
`publication_eligible:false`. It does not qualify full class skill kits, model
performance, or the separate native XP-window ledger.

| Bound | V1, unchanged | V2 |
| --- | ---: | ---: |
| Executor wall ceiling | 120 seconds | 180 seconds |
| Input action ceiling | 128 | 256 |
| SDK request ceiling | 600 | 900 |
| Capture ceiling | 125 seconds | 185 seconds |

Each contract freezes one of the same four class toolkits, an exact baseline
hash and either `active` or `idle`. V2 retains the existing targeting, buff
order, range checks, waits and potion policy. The active recipe increases its
finite loop allowance; idle issues no physical input. Both use the existing
post-render encoded-frame policy and ordinary save/restoration lifecycle.
Historical contracts and generated programs retain their exact bytes.

## Duration and interpretation

The V2 JavaScript clock targets **176 seconds** from program entry. New input
requests stop before **172.5 seconds**; an observation-only tail then fills the
remaining recipe time. Death, rejected input or a runtime failure can end it
earlier. The executor's 180-second deadline starts before Docker/Node launch,
so the recipe leaves four seconds of launch/settlement headroom. This headroom
is not a deadline extension; unusually slow startup still fails closed.

Describe this as an **about-three-minute experiment with a 180-second ceiling**,
not 180 seconds of continuous input. Reports and players must show actual
program and recording durations, including the passive tail. A fixed-step
client-clock repair needs its own source/binary identity and measured native
verification; the longer recipe alone does not repair animation speed.

Capture verification accepts an explicit **185,000ms** independent decoder
bound only with the encoded-frame policy. Existing decoder memory, CPU,
subprocess, frame, byte and corruption checks remain unchanged. Owner and
capture identities must still agree; an API identity cannot be substituted for
this zero-model protocol.

## Readiness

Focused offline tests execute the real generated JavaScript with a fake clock,
exercise private bridge dispatch/worker and inventory receipt paths, and verify
an encoded three-minute capture bundle against packet timestamps and hashes.
These test fixtures are not gameplay or published run evidence. All eight V1
class/control contract and program hashes are regression-pinned, alongside the
earlier native acceptance versions.

Execution requires a separately frozen private maintenance-wrapper successor:
the existing V1 wrapper hardcodes 120/125-second bounds and must stay unchanged.
The new wrapper must bind V2, forward the exact 180/185-second bounds, invoke
the decoder with `maximum_ms=185000` and the frozen encoded policy, and preserve
owned locks, ordinary logout, source/fixture pins, cleanup reserve and one-shot
operation semantics. Frozen V1 results remain available under their original
identities. Source tests alone do not authorize or attest a new live run.
