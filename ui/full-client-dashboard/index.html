The agent loop

Agent SDK

SDK source

Model-authored JavaScript observes the world and sends ordinary game inputs.

sdk.observe()
Read position, HP/MP, XP, level, map and nearby monsters as structured state.
sdk.pressKeys(keys, ms)
Move, jump, attack and use the skills or potions allowed by the fixture.
sdk.wait(ms)
Pause the program while the game keeps running.

Only model-written code runs in the networkless Docker sandbox. The host controller validates SDK requests over stdin/stdout and makes the model API calls.

Example program

const { character } = await sdk.observe();
if (!character.alive) return;

if (character.hp < character.maxHp / 2) {
  await sdk.pressKeys(['HP_POTION'], 100);
}
await sdk.pressKeys(['LEFT'], 300);
await sdk.pressKeys(['PRIMARY_SKILL'], 650);
await sdk.wait(250);

Gameplay recordings are for human review.

Distributed simulation environment

Runtime docs

Frozen comparison groups are assigned to separate worker VMs. Each worker runs one trial at a time in its own game world.

Isolation over shared worlds
A trial cannot change another worker’s monsters or saved state. Separate worlds cost more compute, but allow independent resets and parallel runs.
Controlled comparisons
Models in a group use the same worker and restored character baseline. Inference counts toward the time budget; live combat can still vary.
Traceable results
The worker runner records each attempt and stops on failure. XP is checked after logout, with input receipts and recordings to inspect what happened.
What each run records Storage, metrics and publication
Game state
One MySQL database per worker, restored before each trial. Initial and final character snapshots plus the server’s save receipt establish the saved XP.
Run evidence
Private files keyed by attempt ID retain the phase journal, model requests and responses, generated programs, SDK receipts, capture measurements and WebM recording. Resetting the game database leaves these files intact.
Performance metrics
Inference and execution time, token usage, model-call counts, SDK requests and acknowledged inputs are recorded per run, with per-cycle detail for adaptive runs. Capture evidence also records frame counts and gaps.
Public results
The publisher rechecks the evidence and exports selected metrics to results.json, alongside verified recordings and file hashes. Raw prompts, programs and private logs stay outside the public site. Publication docs

Provisioned with OpenTofu and Ansible on DigitalOcean / Ubuntu. Worker assignment is operator-managed; trial execution is automated locally. A worker’s world stays locked through verification and cleanup.

Experimental design

Starting state
Restore the worker’s database before each trial. Class, level, equipment, inventory, map and key bindings are fixed within a comparison.
Agent interface
Models receive the same class-specific prompt and SDK within a comparison. They read structured state and write JavaScript that issues normal game inputs.
Time and isolation
Planning, inference, execution and waits share one deadline. A worker’s world is locked for the trial; other workers can run independently.

Outcome and verification

ΔXP = XPsaved − XPstart

The score preserves zero gains and losses, including death penalties. This pilot scorer requires the same starting and final level; it rejects unsupported level transitions.

Evidence behind the number

The verifier checks the restored baseline, normal logout, server save receipt and final database snapshot. Cycle receipts bind the returned model, generated programs and acknowledged inputs. Recording publication is checked separately.

How to interpret the results

  • Compare within a class. Different fixtures have different XP opportunities. Raw XP is not averaged into an overall score.
  • One trial is a pilot. With n = 1 per model–fixture pair, run-to-run variance and confidence intervals are not estimated. Frozen inputs do not fix live spawns or combat randomness.
  • The harness is part of the result. Inference latency consumes the budget, and available skills depend on this client/server port. Input receipts establish requests, not successful casts or damage.
Budget and failure policy

The published full-horizon policy admits a new model call only with at least 75 seconds left: up to 50 for inference, 20 for execution and 5 for settlement. After that window closes or an aggregate limit is reached, the controller only observes until the deadline. Death, cancellation or failure can end a trial early.

Zero-XP runs and generated no-ops remain visible. Missing or unverified XP stays unknown, rather than becoming zero. Failed and recovered attempts remain in the history; persistence scores and publication checks are reported separately.

Next protocol Planned · not used for these scores

The research direction is a 30-minute budget with peak normalized XP/min measured in complete, authoritative 15-second windows. Saved start/end XP cannot reconstruct those peaks.

A scored skill suite also needs fixed objectives and verified success criteria. Repetitions, run order, failure handling and aggregation must be declared before a comparative evaluation. The current skill experiments remain exploratory and unscored. Research framing ↗
